# perricheno · Status

Страница состояния инфраструктуры по предоставленному референсу. Cloudflare Worker обслуживает API, Static Assets — интерфейс, Durable Object проверяет сервисы с выбранным интервалом (по умолчанию каждую секунду), приватный R2 bucket хранит минутные сводки истории. Первый сервис: **https://api.perricheno.com**.

Inter и Morphicons поставляются локально вместе с сайтом — без запросов к внешним CDN. Без React. Светлая и тёмная темы, адаптация под телефон и ПК, сохранение темы, круговой переход, плавные переключатели периодов, анимации столбцов и соседних столбцов при наведении. История работает с мышью, касанием, горизонтальным движением пальца и клавишами ← / → / Home / End / Escape. Учитывается `prefers-reduced-motion`.

## Локальный запуск

Нужен Node.js 22+ (рекомендуется 24).

```sh
npm ci
cp .env.example .env
npm start
```

Открыть http://localhost:8787. Первая проверка выполняется при старте, дальше с выбранным в Admin интервалом, по умолчанию раз в секунду. История сохраняется в `./data`. Сервер слушает `0.0.0.0`; для запуска только на localhost задайте `HOST=127.0.0.1`.

Для проверки именно Cloudflare runtime и локального R2:

```sh
cp .dev.vars.example .dev.vars
npm run dev
# Открытие сайта запускает секундный цикл. Можно также активировать его вручную:
curl 'http://localhost:8787/__scheduled?cron=*+*+*+*+*'
```

## Cloudflare Workers + R2

```sh
npm ci
npx wrangler login
npx wrangler r2 bucket create perricheno-health-history
npm run deploy
```

Результат деплоя — адрес `https://health.<ваш-subdomain>.workers.dev`. Для собственного домена используйте Worker → Settings → Domains & Routes. R2 должен быть включён в аккаунте. Создание ресурсов и публикация не выполняются командами `test` или `build`.

Конфигурация находится в `wrangler.jsonc`:

- `HISTORY` — R2 binding на `perricheno-health-history`; bucket не нужно делать публичным.
- `ASSETS` — папка `public/`; запросы `/api/*` обрабатываются Worker.
- `MONITOR` — SQLite-backed Durable Object `MonitorCoordinator`, создаётся миграцией `v1` при деплое. Хранит актуальные замеры, настройки, сессии и ограничение попыток входа.
- Durable Object Alarm запускает следующий цикл с выбранным интервалом. Открытая страница не нужна. Первый запрос к API или минутный Cron активирует планировщик.
- `* * * * *` — резервный Cron для запуска/восстановления планировщика, а не частота проверок. Cron использует UTC.
- `keep_vars: true` сохраняет переменные, заданные через Cloudflare Dashboard. `SERVICES_JSON` и `SITE_NAME` намеренно не заданы в `vars`, чтобы новый деплой не перезаписывал настройки Dashboard.

В R2 → bucket → Settings → Object lifecycle rules создайте правило для префикса **`history/`**, удаление через **32 дня**. API показывает максимум 30 дней; без этого правила более старые объекты продолжат храниться. В Docker очистка старых файлов выполняется автоматически.

Документация: [Static Assets](https://developers.cloudflare.com/workers/static-assets/binding/), [R2 bindings и API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/), [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/).

## Добавление сервисов через ENV

Cloudflare: Worker → Settings → Variables and Secrets → **`SERVICES_JSON`**, тип Text либо Secret, если в списке есть приватные адреса или заголовки. Docker: измените `.env` и выполните `docker compose up -d --force-recreate`.

```json
[
  {
    "id": "api",
    "name": "API (api.perricheno.com)",
    "url": "https://api.perricheno.com",
    "method": "GET",
    "timeoutMs": 10000,
    "degradedMs": 1500
  },
  {
    "id": "frontend",
    "name": "Frontend",
    "url": "https://example.com/health",
    "expectedStatus": 200
  }
]
```

| Параметр | Назначение |
| --- | --- |
| `id` | Стабильный уникальный ключ: `a-z`, цифры, `_`, `-`. Смена ID начинает отдельную историю. |
| `name` | Публичное название карточки. |
| `url` | HTTP/HTTPS endpoint. Публичный API его не раскрывает. |
| `method` | `GET` по умолчанию; можно `HEAD`. |
| `expectedStatus` | Один ожидаемый HTTP-код. Если не задан, 200–399 считаются доступностью. |
| `timeoutMs` | Таймаут 100–15000 мс; по умолчанию 10000. |
| `degradedMs` | Порог медленного ответа; по умолчанию 1500 мс. |
| `headers` | Необязательный объект заголовков для авторизации health-check. Не попадает в публичный API. |

До 20 сервисов; проверки идут пакетами по пять. Редиректы **не переходятся**: 3xx означают, что исходный endpoint отвечает. Для проверки приложения укажите конечный `/health` endpoint и `expectedStatus: 200`. Тайминг измеряется до получения заголовков, тело ответа не скачивается целиком.

`SITE_NAME` меняет имя в описании страницы и заголовке вкладки. Без ENV проверяются `api.perricheno.com` и четыре сервиса Egin; `SERVICES_JSON=[]` показывает пустой список.

## Как считается история

- Периоды: `1m`, `5m`, `24h`, `7d`, `30d`; каждый разбит на 48 равных интервалов.
- `1m` — **одна минута**, не месяц. В секундном режиме в нём примерно 60 замеров. Последние 6 минут хранятся с секундной детализацией; R2 хранит минутные сводки с числом замеров, успешных ответов и суммой задержек. Серая полоска означает отсутствие наблюдений.
- Uptime = доля успешных и медленных успешных HTTP-проверок среди записанных проверок. Это выборочная доступность, не точная длительность простоя. Рядом показывается покрытие неполной истории.
- Если в интервале есть сбой, его полоска красная; иначе медленный ответ — янтарная, успешные — зелёная. Подсказка показывает среднее время ответа, число проверок и последний HTTP-код в интервале.
- Текущий статус становится неизвестным, если последняя проверка старше трёх интервалов (минимум 15 секунд). История не дорисовывается за периоды до запуска или при остановке мониторинга.
- `Refresh` обновляет данные страницы. Посетитель не может запустить проверку ваших сервисов через публичный API.
- Браузер получает актуальный статус через `/api/live` каждую секунду в активной вкладке. История `1m`/`5m` также обновляется раз в секунду; длинные периоды — каждые 30 секунд. Ответы не кешируются браузером. Durable Object кеширует только сводки длинных периодов до 30 секунд.
- R2 хранит один JSON-объект на UTC-день, обновляемый примерно раз в минуту. Минутные сводки учитывают все секундные замеры. Условная запись по ETag и замена сводки по ключу минуты не удваивают данные при повторе архивирования. Старые записи минутного мониторинга совместимы.
- Пока R2 недоступен, неархивированные сводки сохраняются в Durable Object; архивирование повторяется на следующей минуте. Настройки и свежие замеры переживают перезапуск объекта. Одновременно выполняется только один цикл: медленные ответы могут увеличить фактический интервал. Это best-effort периодичность, не гарантия запуска точно через 1000 мс.

HTTP health-check контролирует доступность указанных URL с точки проверки. Чтобы проверить Workers, R2 или другие зависимости приложения, его `/health` должен проверять эти зависимости и возвращать соответствующий HTTP-код. Это не заменяет Cloudflare Status и не проверяет содержимое bucket автоматически.

## Docker

```sh
cp .env.example .env
docker compose up -d --build
```

Открыть http://localhost:8787. Контейнер работает от пользователя `node`, имеет healthcheck и постоянный volume `health-data`. Compose привязывает порт к localhost; для внешнего доступа используйте reverse proxy или измените привязку. В Docker используется локальное файловое хранилище вместо Cloudflare binding; настройки и сессии сохраняются в `data/state/`, интерфейс и мониторинг общие. При размещении за HTTPS reverse proxy задайте `PUBLIC_ORIGIN=https://ваш-домен`, чтобы проверка Origin и Secure cookie соответствовали публичному адресу. Запускайте **одну реплику** на один volume. Docker не нужен для деплоя Worker.

## Проверки

```sh
npm test                    # проверки мониторинга и API
npm run build               # dry-run сборки Worker, без публикации
npx playwright install chromium
npm start                   # отдельный терминал

```

Для существующего браузера можно задать `CHROME_PATH=/path/to/chrome`, для другого адреса — `TEST_URL`. Скриншоты сохраняются в игнорируемый `test-results/`. Фикстура полной зелёной истории используется **только в браузерных тестах**, не в приложении.

Палитра светлой темы снята с исходного JPG: фон `#F1F1F3`, карточка `#FFFFFF`, зелёный `#02D183`. Тёмная тема подобрана по второму скриншоту: `#0A0A0A` и `#111113`. Исходная фотография, `.env`, токены и локальная история исключены из Git и Docker-контекста.

## Admin: вход по четырём цифрам

Маленькая кнопка **Admin** находится внизу страницы. Вход: **0000**. Четыре точки, цифровая клавиатура, ввод с физической клавиатуры и Backspace. После четвёртой цифры код проверяется сервером. В интерфейсе выберите **1 / 5 / 10 / 30 / 60 секунд** и нажмите **Save changes**. Настройка общая для всех посетителей и сохраняется после перезапуска/деплоя. **Lock admin** завершает сессию.

Чтобы изменить PIN, задайте Cloudflare Secret `ADMIN_PIN` (ровно четыре цифры), либо переменную в Docker `.env`. Если переменная не задана, используется запрошенный PIN `0000`. PIN не передаётся в публичном API и не включён в клиентский JS. По вашему запросу код по умолчанию присутствует в серверном исходнике публичного репозитория.

Сессии: случайный токен, HttpOnly + SameSite=Strict cookie, Secure на HTTPS, срок 12 часов. В хранилище остаётся только хеш токена. После пяти неверных попыток — блокировка IP на 15 минут; общий лимит — 30 попыток входа в минуту. Ограничения переживают перезапуск. Проверяется Origin для всех изменений. Смена ADMIN_PIN аннулирует старые сессии.

### Секундный режим на Cloudflare

1 секунда — около **86 400 проверок в сутки на сервис** при быстрых ответах. Для непрерывного секундного режима этой реализации нужен **Workers Paid**: один Durable Object Alarm в секунду плюс сохранение состояния превышают бесплатный лимит 100 000 записей строк в день. Запросы посетителей дополнительно расходуют лимит запросов. Код не меняет тариф аккаунта автоматически. [Лимиты и тарификация Durable Objects](https://developers.cloudflare.com/durable-objects/platform/pricing/). На Docker этих лимитов Cloudflare нет.

Cloudflare Alarms могут задерживаться при обслуживании платформы; медленный health endpoint также увеличивает интервал. [Семантика Alarms](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#alarms).

## Живые деплои Egin

Четыре сервиса Egin включены в конфигурацию по умолчанию и `.env.example`:

| ID | Адрес | Endpoint проверки | Окружение |
| --- | --- | --- | --- |
| `egin-web` | `egin.perricheno.com` | `/api/health` | production |
| `egin-api` | `api-egin.perricheno.com` | `/openapi.json` | production |
| `egin-dev-web` | `dev-egin.perricheno.com` | `/api/health` | staging |
| `egin-dev-api` | `dev-api-egin.perricheno.com` | `/openapi.json` | staging |

Staging-портал в действующем конфиге Egin — **dev-api-egin.perricheno.com**, не api-dev-egin.perricheno.com. Если SERVICES_JSON уже задан в Cloudflare, добавьте эти записи к своему списку: переменная по-прежнему является явной конфигурацией.

На странице появился блок Deployments с последним запуском каждого окружения. В нём: этап, число завершённых этапов (не выдуманный процент времени), commit, длительность, раскрываемая шкала этапов и поток событий. У затронутых сервисов появляется кнопка состояния выкладки. Деплой не превращает успешную health-проверку в сбой и не скрывает настоящий сбой.

Транспорт — **Server-Sent Events**, `/api/deployments/stream`. Новые события сразу отправляются всем подключённым страницам. После разрыва EventSource переподключается и получает полный сохранённый снимок; при недоступности потока включается опрос `/api/deployments` раз в 5 секунд. В фоновой вкладке поток закрывается и восстанавливается при возвращении. Медленному клиенту не накапливается неограниченная очередь.

Реальные события отправляет `deploy/health_reporter.py`, подключённый к `/root/egin/deploy/manage.py`. GitHub Actions в Egin запускает проверки, а не выкладку, поэтому его статус не используется как признак живого деплоя. Поддерживаются обычная выкладка, reuse-images, ошибка, отмена и откат. На Health сохраняются 12 последних запусков и до 160 событий каждого. Последний запуск окружения показан на странице; остальные доступны через API.

### Подключение отправителя

1. Войдите в Admin (`POST /api/admin/login`, JSON `{"pin":"0000"}`; запросы с Origin вашего сайта).
2. С тем же HttpOnly cookie выполните `POST /api/admin/deploy-token`, JSON `{"project":"egin"}`. Сильный токен возвращается один раз; сервер хранит хеш. Повторный выпуск отзывает прежний токен проекта.
3. На сервере Egin запишите URL `/api/deployments/ingest`, project `egin` и токен в `deploy/state/health.json` с правами 0600. Файл исключён из Git и Docker-контекста. Формат описан в `deploy/HEALTH.md` репозитория Egin.
4. Обычная команда `python3 deploy/manage.py deploy staging` начнёт поток. Отдельный деплой ради проверки интеграции не требуется: событие `{"project":"egin","type":"ping"}` с Bearer-токеном проверяет соединение без создания ложной выкладки.

Альтернатива для настройки без admin API — Cloudflare Secret `DEPLOY_INGEST_TOKEN` (не менее 32 случайных символов) и такой же токен у отправителя. Токен, выданный через admin API, имеет приоритет. PIN администратора **не является токеном отправителя**.

В публичный поток принимаются только фиксированные коды событий и числовой прогресс сборки: произвольные `message`, `raw`, stdout/stderr не публикуются. Последовательность проверяется; дубликаты идемпотентны, пропуски/запоздалые изменения завершённого запуска отвергаются. Успех допускается только после завершения всех этапов. Без heartbeat 90 секунд показывается Updates lost; при восстановлении отправки состояние возвращается к реальному. Сам сервис мониторинга не запускает команды выкладки.

Для других проектов доступна переменная `DEPLOY_PROJECTS_JSON` — массив объектов `{id,name,repository,services:{production:[serviceIds],staging:[serviceIds]}}`. ID сервисов должны совпадать с SERVICES_JSON. По умолчанию подключён Perricheno/egin.
